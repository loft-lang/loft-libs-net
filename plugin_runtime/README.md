# ZT-E — signed-WASM plugin runtime (staging)

Implements [@PLN84 § ZT-E](../../doc/claude/plans/84-zero-trust-libs.md):
collaborative-editing plugins as **signed WASM modules**, loaded host-side
(`wasmtime`) and browser-side (`WebAssembly.instantiate`) behind the **same
Ed25519 signature gate**.

Staged here because the home library is TBD (`loft-libs-net` or a new
`loft-libs-plugins` chunk). The design + the load-bearing invariant are in
[DESIGN.md](DESIGN.md); this file is the map of what is here and where each
piece ultimately belongs.

## The security gate (the whole point)

> No byte of plugin code runs unless a **trusted** Ed25519 public key verifies
> the signature over the **exact** module bytes that will be instantiated —
> the verify is the single gate every load path passes through, **before**
> instantiation, and it fails **closed**.

The signature is a raw 64-byte Ed25519 over the raw wasm bytes; a trusted author
is a 32-byte raw Ed25519 public key. This is the **same signing path the loft
registry trust root already ships** (`loft-keygen sign` / `src/registry_keys.rs`),
reused rather than reinvented — and it directly implements PLUGINS.md §9c.5.

| Path | What | Ultimately lives in |
|---|---|---|
| `DESIGN.md` | The design + invariant + failure-path enumeration (design-protocol) | the plugin library's design doc |
| `reference-plugin/src/plugin_abi.loft` | **E1** — the six-export ABI as a loft `interface` (the canonical contract) | plugin lib `src/` (the public `Plugin` interface) |
| `reference-plugin/src/counter_plugin.loft` | **E1** — the reference plugin logic (a CRDT counter) in loft source | a `reference-plugins/` example |
| `reference-plugin/src/counter_demo.loft` | proves the counter logic on the loft interpreter | the lib's `tests/` |
| `reference-plugin/wasm-shim/` | **E1** — Rust shim exposing the six named wasm exports (stand-in until loft codegen can emit named library exports — see DESIGN.md § Follow-up) | replaced by `loft --native-wasm --exports` |
| `host-loader/src/lib.rs` | **E2** — `verify_then_load` (the gate) + `PluginInstance` (the six-export driver) | the loft **server** binary's plugin subsystem |
| `host-loader/src/main.rs` | **E2** — `load-plugin` CLI front-end | a `loft plugin run` subcommand / server internals |
| `host-loader/tests/security_gate.rs` | **E2** — the four-case (+boundary) negative test | the server's plugin test suite |
| `browser-loader/plugin_loader.mjs` | **E3** — the same gate in JS over WebCrypto Ed25519 + the six-export driver | the browser client's plugin host |
| `browser-loader/security_gate.test.mjs` | **E3** — the same four cases under Node 22 | the browser client's test suite |
| `build/sign-and-build-fixtures.sh` | builds the wasm + generates keys + signs (reproducible) | the lib's `xtask` / CI |
| `build/counter_plugin.wasm` + `.sig`/`.sigB` | committed test fixtures | regenerated by the build script |
| `keys/author{A,B}/public_key.hex` | **test-only** Ed25519 **public** keys (committed; the tests' trusted-key hex) | never production keys |
| `keys/author{A,B}/registry-signing-key.bin` | the **private** keys — **gitignored** (repo root `.gitignore`), regenerable | never committed, ever |

> The keys under `keys/` are throwaway TEST keys generated by the build script.
> Only the **public** keys (`public_key.hex`) are committed — enough for the
> committed `.wasm` + `.sig` fixtures to verify in CI. The **private** keys are
> gitignored (the repo root blocks `registry-signing-key.*` so real registry
> keys can never be committed); re-run the build script without `--keep-keys` to
> regenerate them and re-sign. Production trusted-author keys come from the
> bundled signed list + the user's `trusted_plugin_author` records (§9c.5).

## Build + run everything

```bash
# 0. prereqs: loft-keygen + the wasm target
cargo build --release --bin loft-keygen --features registry   # from the loft repo root
rustup target add wasm32-unknown-unknown

# 1. build the reference plugin wasm + generate keys + sign (reproducible)
tools/zt-e-plugin-staging/build/sign-and-build-fixtures.sh --keep-keys

# 2. E1 — prove the plugin logic on the loft interpreter
loft tools/zt-e-plugin-staging/reference-plugin/src/counter_demo.loft

# 3. E2 — the host security gate (the load-bearing negative test)
cd tools/zt-e-plugin-staging/host-loader && cargo test --release --test security_gate

# 3b. E2 — the CLI end-to-end (ACCEPT case)
cargo run --release --bin load-plugin -- \
  ../build/counter_plugin.wasm ../build/counter_plugin.wasm.sig \
  "$(cat ../keys/authorA/public_key.hex)"

# 4. E3 — the browser security gate (same four cases, WebCrypto Ed25519)
node tools/zt-e-plugin-staging/browser-loader/security_gate.test.mjs
```

## The four mandated cases (E2 + E3, identical decisions)

| Case | Input | Host (E2) | Browser (E3) |
|---|---|---|---|
| F1 signed | A's signature, trust = {A} | **ACCEPT** + counter runs to 12 | **ACCEPT** + counter runs to 12 |
| F2 tampered | one wasm byte flipped | **REJECT** (Untrusted) | **REJECT** (Untrusted) |
| F3 unsigned | empty / short / bogus signature | **REJECT** (MalformedSignature / Untrusted) | **REJECT** (same) |
| F4 wrong-key | B's valid signature, trust = {A} | **REJECT** (Untrusted) | **REJECT** (Untrusted) |

Both test harnesses are proven **non-vacuous**: temporarily forcing the gate
fail-open turns exactly the rejection cells (F2/F3/F4) red while the accept
cells stay green — the rejection is the only reason those cells pass.
